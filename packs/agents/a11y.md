# Accessibility (a11y) guardrails (Copilot / Claude / Codex)

Use with [core.md](core.md) and [testing.md](testing.md). For agents changing UI, docs sites, CLI help text, or any human-facing surface.

## Defaults

- Prefer **semantic** structure (headings, landmarks, labels) over div-only layouts when the stack supports it.
- Do not rely on color alone to convey meaning; keep contrast readable for body text and controls.
- Keyboard users must reach interactive controls without a mouse-only dead end.
- Images and icons that convey meaning need alt text or an accessible name; decorative ones should be marked decorative.

## Before coding

1. Name the surface (web UI, docs, CLI, PDF export) and who must use it without a pointer or with assistive tech.
2. List existing a11y tests, lint rules, or design tokens the consumer already uses—do not invent a new toolkit mid-slice.
3. Note any intentional exceptions for a follow-up issue (do not silently skip).

## While coding

- Wire labels to inputs; keep focus order logical after DOM changes.
- Preserve skip links / landmarks if the consumer already has them.
- Announce dynamic updates only when the product already uses live regions—do not spam polite noise.
- For CLIs: keep `--help` accurate; avoid requiring color to understand errors.

## Slice checklist

- [ ] Interactive controls have accessible names
- [ ] Color is not the only signal
- [ ] Keyboard path exists for new controls
- [ ] Meaningful images have alt / accessible names
- [ ] No new flashing or auto-playing media without controls

## Do not

- Ship icon-only buttons with empty accessible names
- Remove focus outlines “for aesthetics” without a visible replacement
- Invent WCAG scores or audit tools the repo does not run
- Paste real user PII into a11y fixtures

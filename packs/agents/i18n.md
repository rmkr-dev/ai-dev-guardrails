# Internationalization (i18n) guardrails (Copilot / Claude / Codex)

Use with [core.md](core.md), [docs.md](docs.md), and [a11y.md](a11y.md). For agents changing user-visible strings, locales, or RTL layouts.

## Defaults

- Prefer the consumer’s existing i18n library and message catalog format—do not introduce a second system mid-slice.
- Keep user-facing strings out of business logic when the repo already externalizes them.
- Do not invent locale codes, translation vendors, or pluralization rules the project does not use.
- Examples and fixtures must remain honest for the default locale shipped in the PR.

## Before coding

1. Identify where strings live (catalogs, YAML, gettext, frontend JSON).
2. Note whether CI already checks for missing keys.
3. Call out RTL / plural / date-format impact if the surface is locale-sensitive.

## While coding

- Add keys with stable IDs; avoid concatenating translated fragments when the catalog style forbids it.
- Update catalogs and consuming code in the same PR.
- Keep placeholder/interpolation syntax consistent with existing messages.
- Do not hardcode a new default language without an ADR or human approval.

## Slice checklist

- [ ] New strings use the existing catalog mechanism
- [ ] Missing-key checks (if any) still pass
- [ ] Interpolation/plural forms match project conventions
- [ ] Screenshots/docs updated for visible copy changes when the repo expects that
- [ ] Human approval for new locales or vendor tooling

## Do not

- Ship English-only hardcoded UI in a repo that already externalizes strings
- Machine-translate into the catalog without labeling quality
- Break RTL layout “temporarily”
- Invent company-specific product locales in examples

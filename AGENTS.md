# Agent and human guardrails

Read this file before you change **ai-dev-guardrails**. Rules apply to people and to coding agents (Copilot, Claude, Codex, and similar).

This repository distributes **installable** guardrail packs. Keep the packs useful out of the box; do not weaken defaults without an explicit decision recorded in an ADR.

## Before you write code

1. Read `README.md`, this file, and any docs that touch your change (`docs/architecture/`, `docs/decisions/`, `docs/references/` including pack-matrix and validator-checks, `packs/`).
2. State the slice you are completing. Prefer one reviewable PR with 2–4 commits.
3. Prefer the smallest change that is **correct and complete** for that slice. Do not drive-by refactor.

## Human-first

- Write for a reviewer who was not in the session: commits, PR body, and docs must stand alone.
- High-impact changes (license, security defaults, public CLI API, CI required checks) need **human approval** before merge. An agent may draft; a person decides.
- No Cursor/AI co-author trailers or “generated by” tags in commits.

## Complete across layers

A slice is not done if you updated only one layer. When the change needs them, update together:

- pack content or validator behavior
- tests
- CI / repo automation
- docs that describe the behavior
- an ADR, if the shape of the system changed

Do not add a file that nothing references, or a doc that describes a file that does not exist.

## No orphans, no speculation, no fakes

- **No orphans:** every new doc, pack module, or workflow has a reader and a reason.
- **No speculative engineering:** do not add frameworks, sample apps, or “future-proof” abstractions for slices that are not in scope.
- **No fake implementations:** no stub CLIs that pretend to work, no badges for CI that is not running, no architecture of systems that are not in this repo.
- **Docs match reality.** If a feature is planned, say it is planned.

## Scope boundaries

- This pack complements `llm-eval-harness` and `enterprise-github-template`; do not duplicate their primary purpose.
- **No Node/npm.** Python only for the optional validator.
- **No secrets** in the repo, examples, or commit messages.
- **No company names** in docs or examples.

## Tests and CI

- When application or validator code exists, tests ship in the same PR as the behavior.
- Prefer GitHub Actions and reusable workflows from `rmkr-dev/gha-reusable-workflows` when CI is added.
- GitHub Free-first: do not depend on paid features or third-party secrets for the default green path.

## Definition of done (repo changes)

A change is done when all of the following are true:

- [ ] Scope matches the agreed slice; nothing extra landed “for later convenience”
- [ ] Behavior, tests, automation, and docs that this slice requires are present and consistent
- [ ] No secrets, personal contact details, or leftover placeholders that claim to be finished
- [ ] `README.md` and linked docs still describe the repo as it is
- [ ] Consumer-visible changes are noted in `CHANGELOG.md` when that file exists
- [ ] Significant decisions have an ADR under `docs/decisions/`
- [ ] High-impact items are called out for a human reviewer
- [ ] Local validation passes when tooling applies (`pytest`, `ai-guardrails check .`)
- [ ] You could merge this PR and leave the repo coherent if no further PR ever shipped

## Final self-review

1. Diff the PR as a stranger. Is anything unexplained?
2. Grep for names of files you added. Are they linked from `README.md` or the right index?
3. Confirm you did **not** add Node/npm or company-specific content.
4. Confirm commit messages are conventional and read like a person wrote them.
5. Re-read this file. Fix anything that now contradicts it.
